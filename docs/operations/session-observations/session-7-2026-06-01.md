## Race Condition: PHASE8-006 — Observed In Production (10:00 IST)

### What Happened

Two distinct signals for ETERNAL fired within 1 second of each other, both approved
against a FLAT position, resulting in an unintended net LONG +101 position.

### Full Trade Sequence

```
04:19:51 UTC  BUY  ETERNAL  qty=+201  @ ₹248.80  signal=13478aa579f640f3e7c3  → LONG +201
04:23:35 UTC  SELL ETERNAL  qty=-201  @ ₹248.89  [exit-auto TAKE_PROFIT]      → FLAT
                                                                                  ↑
04:27:42 UTC  SELL ETERNAL  qty=-100  @ ₹248.00  signal=cfbd2a9520d448302f89  → SHORT -100
04:27:43 UTC  BUY  ETERNAL  qty=+201  @ ₹248.50  signal=895d02b1646f761b5f6b  → net LONG +101  ← RACE
```

Signal A (SELL 100) and Signal B (BUY 201) arrived 1 second apart. Both had unique
`signal_id` hashes so the idempotency gate did not block either. Both were validated
by risk_engine against a FLAT ETERNAL position — Signal B's risk check ran before
Signal A's `apply_fill_to_position` write landed in DynamoDB.

**Resulting net position:** LONG +101 ETERNAL @ ₹248.99 (weighted avg of two fills).  
**Intent:** Strategy meant to open SHORT -100 and LONG +201 as independent positions,
not a net LONG +101.

### Root Cause

1. `_signal_locks` in execution_engine is keyed by `signal_id`, not `symbol`. Two
   different signals for the same symbol run concurrently — no symbol-level serialisation.

2. `signal_inbox.py` / `signal_outbox.py` (PHASE8-006) are absent. The inbox/outbox
   pattern would serialise per-symbol: Signal B for ETERNAL would queue behind Signal A
   until A's fill committed to DynamoDB, at which point the risk check would see
   SHORT -100 and apply the correct position-limit logic.

### Blockers This Evidence Supports

| Blocker | Status | Evidence |
|---------|--------|----------|
| PHASE8-006 — signal_inbox/outbox absent | 🔲 OPEN | This race — two signals 1s apart, both approved against stale FLAT state |
| HIGH-001 — `_signal_locks` keyed by signal_id not symbol | ✅ Fixed (ADR-022) — but lock granularity still per-signal, not per-symbol | Race still possible between distinct signals |

### Impact This Session

- **Paper mode only** — no real capital at risk.
- Position is managed: TEE exit policy attached, MIS will close at 15:05 IST.
- **Concrete, reproducible evidence** of the race: observable in execution_engine logs
  at `04:27:42` and `04:27:43` UTC.

### Suggested Fix (PHASE8-006)

Implement `signal_inbox.py` with a per-symbol asyncio lock (or DynamoDB conditional
write) that serialises signal processing at the execution layer:

```
Signal arrives at execution_engine
  → acquire symbol lock (ETERNAL)
    → read current position
    → validate against live position (not risk-engine snapshot)
    → fill or reject
  → release symbol lock
```

Until PHASE8-006 is implemented, the race is mitigated (but not eliminated) by the
risk engine's position-limit validator, which rejects the second signal if the first
fill has already written to DynamoDB before the second signal's risk check runs.
